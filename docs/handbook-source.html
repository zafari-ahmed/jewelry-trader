Section 1

What this application is

One system covering the whole life of a piece: intake and appraisal, the shop counter, the public storefront, and the money that follows — wages, refunds and the audit trail behind them.

Jewelry Trader serves dealers in antique, vintage, estate, designer and fine jewelry, across several store locations and several salespeople. A piece is photographed and catalogued once, then travels through review, listing, sale and — if it comes back — return, with every step recorded against the person who took it.

The defining characteristic

Almost nothing is hardcoded. Payment providers, commission structures, tax rates, required-field rules, discount ceilings, retention windows and feature availability are all configured from the admin panel by a Super Admin. No code change, no redeploy.

What that means in practice

Stripe keys
Stored encrypted in the database, rotated through a form. Not in .env.
Which fields are mandatory
A table of rules, editable per item category. A ring can require a size; a brooch cannot.
Commission structure
Four plan types, per-salesperson assignment, with a configurable fallback.
Sales tax
Per location, US state-based, recorded on each order as charged.
What .env holds
Database credentials, mail transport, app key. Infrastructure only — verified.

The four surfaces

SurfaceWho uses itWhat it does

Point of SaleSales staff at the counterFull-screen register: search, cart, discounts, split payment, returns, exchanges, receipts

One codebase, one payment path. The register and the storefront both create orders through the same service and take money through the same gateway factory. A change to how money is handled happens once.
Section 2

Getting started

From a fresh clone to a working till, and the order in which to set things up.

Installation

Install dependencies and build assets

composer install  ·  npm install  ·  npm run build

Point the application at a database

Copy .env.example to .env, set the database credentials, then run php artisan key:generate.

Create the schema and seed it

php artisan migrate --seed

Seeds six roles with 34 permissions, 45 settings at their defaults, four locations, the Stripe gateway row, 29 field rules across six categories, and placeholder step-up symbols.

Link storage and start

php artisan storage:link  ·  php artisan serve

Run the queue worker

php artisan queue:work

Commission calculation runs here. Without a worker, sales still complete — commissions simply wait in the queue.

First-run configuration, in order

WhereWhat to do
1Settings → GeneralCompany name, timezone, receipt footer text.
2Settings → LocationsYour real stores, each with its state and tax rate. Keep the Web location: online orders belong to it.
3Settings → PaymentsPaste the Stripe test keys, leave Test mode on. Live keys go in the separate live fields when you are ready.
4Terminalphp artisan payments:verify — runs a real charge, refund and split against Stripe test mode and reports pass or fail.
5Settings → SecurityWhich roles must use two-factor; session timeout; password policy; retention windows.
6Settings → Field RulesAdjust what each category requires before an item can be submitted.
7Settings → CommissionThe default plan used for any salesperson without an individual agreement.
8Roles & PermissionsCreate staff accounts, assign roles and home locations.

Do this before going live

Replace the seeded step-up answers. The installer seeds three symbols with the answers change-me-one, change-me-two, change-me-three. That challenge guards override approval and payment-key changes. A seeded secret is not a secret.

Section 3

Items: intake, the colour system, and review

The centrepiece workflow. A piece goes from a pile of photographs to a listed item, with the record showing at a glance what is finished and what is not.

The journey of a piece

DraftPhotographed and being catalogued
→
Pending reviewSubmitted; required fields complete
→
ApprovedAccepted for the record
→
ListedPublished for sale
→
SoldClaimed by an order

Approve and List are deliberately two separate actions. A piece can be approved for the record — catalogued, appraised, documented — without being published for sale. Listing is a second, explicit decision.

The colour-coded field system

Every field on an item record carries a status colour. The colours are configuration, held in a rules table and editable per category from Settings, so what a ring must have differs from what a brooch must have.

ColourMeaningBehaviour today
RedRequired, still emptyBlocks submission. Enforced on the server, not only in the browser.
YellowNormally AI-suggestedAn ordinary editable field, marked “AI suggestion available in a future update”.
GreenComplete and validComputed the moment a valid value is entered. Never configured directly.
GrayNot applicableDisabled for this category — chain length on a ring, for instance.
BlueHuman overrideRecorded on the item, so Phase 2's correction log has real data from day one.
○ NeutralOptional, untouchedA sixth state added in build: an empty optional field shows no status, so an unfinished record cannot look complete.

What is recorded about an item

Identity & materials

SKU, title, subtitle, category and subcategory, brand or maker, style period, metal type and purity, weight in grams, measurements, hallmark text, plus any category-specific field a Super Admin adds later.

Condition & description

Condition and restoration notes, internal notes, customer description, and separate SEO, marketplace and social descriptions.

Gemstones

Stone type, shape, cut, colour, estimated carat weight, setting style, and which stone is the principal one. Several stones per piece.

Photographs

Each tagged by type — front, back, side, hallmark, gemstone, clasp, movement, signature, packaging, certificate — with one chosen as the hero shot used on the storefront.

Pricing (append-only history)

Acquisition cost, retail price, insurance value, negotiation floor, promotional price. A price change writes a new row rather than overwriting, so what a piece was previously offered at survives.

Stock & provenance

Which location holds it and in what state (in stock, reserved, sold, transferred); who created, submitted and approved it, and when.

A field that has no column still works. Because a Super Admin can invent a new field rule — say movement_type for watches — values for fields that have no database column are stored as item attributes. Adding a required field to a category needs no developer.

Speed, measured rather than assumed

The specification asks for photo upload through submit-for-review in well under five minutes. Each item records the elapsed time between creation and submission, and the review queue shows managers the median and slowest intake times, with the median turning red if it drifts above five minutes.

Moving stock between locations

A transfer is requested, approved by the sending location's manager, then completed on arrival. Stock does not move until completion, and an approved transfer marks the piece in transit so it cannot also be sold. The stock row moves; it is never duplicated.

Section 4

The counter: sales, returns and exchanges

A full-screen register with the happy path kept to a minimum number of clicks. Target: a complete sale in under two minutes.

Taking a sale

Find the piece

Search by SKU, title or maker, or scan a tag. Only listed, in-stock, unlocked items appear.

Build the sale

Add pieces, plus any custom line item — ring sizing, repairs, a workshop service — which needs no inventory record. Discount a line by percentage or fixed amount.

Take payment

Card, cash, or a split across several tenders. Reaching payment pre-fills a single card tender for the full amount, so the common sale is search → add → charge.

Finish

Receipt on screen, printable on 80 mm thermal stock, and emailed when a customer address is on file. Change due is calculated and shown for cash.

Rules the register enforces

RuleHow it behaves
Tenders must equal the totalThe Charge button stays disabled, and the server re-checks. A part-paid order can never be marked paid.
Discount ceilingAbove the configured percentage, the discount is refused unless the user holds the approval permission. Checked in code, not by hiding a button.
One-of-a-kind stockThe same piece cannot be added twice, and a piece sold elsewhere cannot be added at all.
The sold-once guaranteePaying locks the stock row and flips it to sold inside the same transaction as the order and the payment.
Locked itemsA piece under a sales or full lock cannot be sold, from any surface.

Returns and exchanges

Look up the original sale by order number, tick the items coming back, and choose a refund or an exchange.

  • Refunds return the line's discounted value plus the tax charged on it, capped at what remains refundable. Card refunds reverse through Stripe; cash is unrestricted. The piece goes back on the shelf and returns to listed.
  • Exchanges are a return and a replacement sale in one transaction. Only the difference changes hands — the customer pays the excess, or is refunded it if the replacement is cheaper.
  • Outside the return window (30 days by default, configurable) a refund is refused unless the user has override authority.
Section 5

The public storefront

The same catalogue, the same stock, the same payment path — seen from the customer's side.

Browsing

Keyword search across title, maker, period, metal and description. Filters for category, period, metal and price range; sorting by newest or price. Facets are drawn only from pieces the public can actually see.

The piece

Image gallery with the hero shot first, customer description, specification table, gemstone details, price, and add-to-bag.

The visibility guarantee

Only pieces that are listed, in stock and not locked ever appear publicly. Draft, pending, approved-but-unlisted, archived, sold and reserved pieces are invisible — not merely hidden from the listing, but unreachable by guessing the URL. Seven hidden states are covered by tests.

Checkout

Guests may check out without an account. Card details are entered in Stripe's Payment Element, themed with the shop's own colours and typography, and confirmed by the browser directly with Stripe — card data never reaches this application. The server then re-reads the payment from Stripe before recording it, and refuses any amount that does not match the order. The browser is never trusted about whether money moved.

Sales tax follows the delivery address's state. A state with no store charges nothing rather than guessing.

Customer accounts

Customers sign in on their own separate account system — a customer session can never carry staff permissions. A guest who bought earlier and later registers with the same email claims that record, keeping their order history rather than starting a second one. POS and storefront share one customer record throughout, matched on email.

A piece sold at the counter disappears from web bags. The cart re-checks availability on every view, so a one-of-a-kind item sold in the shop cannot reach checkout online.
Section 6

Payments

One gateway abstraction, keys held in the database, and every figure in whole cents.

How payments are structured

CapabilityDetail
CardCharged through Stripe. At the counter today this uses Stripe's test token — see the open items in Section 10.
CashRecorded with no gateway call; change due calculated from the amount tendered.
SplitSeveral tenders on one sale, in any mix. The parts must sum exactly to the total.
RefundsFull or partial, drawn from card tenders first since cash is unrestricted.
Capture & voidAuthorise, then settle for less or release entirely — backing the exchange flow.
WebhooksSigned endpoint verified against the stored secret, so a refund issued in the Stripe dashboard is reflected here.

Three decisions worth knowing

Money moves before it is recorded. A gateway call cannot be rolled back, so charges happen outside the database transaction and records are written inside it. The reverse order would let a rolled-back transaction hide a real charge.

A failed split reverses what already succeeded. If the second tender is declined, the first card is refunded automatically. A customer is never left charged for a sale that did not complete.

Switching provider is a data change. Gateways are rows naming a driver class. Adding PayPal later is a row plus a class — the code that takes payment does not change.

Verifying the keys

Running php artisan payments:verify performs a real charge, a partial refund, the remainder, a card-and-cash split and a split refund against the configured gateway, reporting each. It refuses to run while Test mode is off, so it can never move real money. Run it after every key rotation.

Section 7

Commission and payroll

Four plan structures, calculated away from the till, with California wage law shaping the design.

The four plan types

TypeBasisWorked example
Sales-basedFlat percentage of the sale5% of a $1,000 sale = $50.00
Profit-basedPercentage of margin over acquisition cost20% of ($1,000 − $450) = $110.00
TieredRate rises at configured thresholds4% below $5,000; 6% of an $8,000 sale = $480.00
SplitA pool divided across several staff5% of $1,000 split 60/40 = $30.00 / $20.00

How it is calculated

  • Tax is never commissionable. Every plan works from subtotal less discount — sales tax was never the shop's money.
  • Discounts reduce the commissionable value, so a discounted sale earns proportionally less.
  • The logged-in salesperson earns it. Web sales attribute to nobody.
  • It runs in the background, queued after the sale commits. Commission arithmetic never sits between a customer's card and their receipt, and never runs for a sale that rolled back.
  • A salesperson without an individual agreement falls back to the default plan configured in Settings.

The rounding problem, solved deliberately

The classic split-commission bug is rounding: three people sharing a pool that will not divide evenly, and a cent goes missing. Shares are floored, then the remainder is handed out one cent at a time to the largest fractional parts. The parts always sum exactly to the pool — checked across forty pool-and-share combinations, including deliberately awkward ones.

California compliance, built in

StatuteWhat the system does
§2751
Written agreements
Each staff assignment stores the agreed terms — text or an uploaded document — alongside the numeric plan. The plan alone is not the agreement, and the system distinguishes the two.
§221
No unlawful deductions
Nothing deducts from an earned commission. A refund leaves the record standing. Any reduction must go through an override — reasoned, approved and logged.
§204
Wage timing
Approval and payment are recorded as separate, timestamped steps, so wage timing is auditable.

Reporting and payroll export

Daily, weekly or monthly, filtered by salesperson, location and status. Staff see only their own figures; managers and accountants see everyone's. Export to CSV is a separate permission.

The export's column mapping is configurable, because the target payroll system's format is not yet known. Changing which columns appear, and what each contains, is a settings change. A column pointing at something the system does not recognise exports a visible marker rather than a silent blank.

Section 8

Security, permissions and the audit trail

Six roles, thirty-four granular permissions, two-factor authentication nobody can skip, and a record of everything.

The six roles

RolePermsRemit
Super Admin34Everything, including settings, roles and overrides
Store Manager21Inventory, orders, approvals, discounts above the staff ceiling, audit, commission reports
Sales Staff11The register, creating and editing inventory subject to approval, own commission
Inventory Specialist7Create, edit and approve inventory for listing. No sales.
Accountant9Financial and commission reports, payment records, payroll export, audit. No inventory edits, no sales.
Customer Service7View orders and customers, process returns. No discounting, no pricing edits.

Nothing in the code checks a role by name — only permissions — so a Super Admin can compose a custom role from the Roles & Permissions page and it behaves exactly like a built-in one.

Multi-factor authentication

Which roles must use it is a setting. A user in one of those roles is sent to enrolment on first sign-in and challenged on every sign-in thereafter. Enrolment issues ten single-use recovery codes, shown once. No role is exempt, including Super Admin — the requirement is enforced across every authenticated page, not route by route.

The authenticator secret is encrypted at rest; recovery codes are additionally hashed, so a database leak yields nothing usable. The enrolment QR code is drawn on the server — the secret never reaches a third party.

The audit trail

Every create, update and delete on products, orders, payments, settings, users, customers, locations, transfers, overrides and locks is recorded automatically — who, what, when, before and after, with IP address and browser. Logging is attached to the models themselves, so a new code path cannot forget to call it.

  • Secrets are masked. A Stripe key rotation is recorded as a change, with the value redacted. A gateway switch stays readable.
  • Non-model events too: sign-in, failed sign-in, MFA passes and failures, step-up attempts, webhook rejections.
  • Retention is split by category. General activity keeps for two years; financial records keep for seven, reflecting IRS recordkeeping. Both are configurable, and a scheduled job applies them nightly.

Overrides

Deliberately high-friction, because this exists for fraud prevention. A reason is required, and nothing takes effect until someone with approval authority approves it. A Super Admin overriding their own request still goes through both steps, and the trail records that they approved their own request.

Inventory locks

LockBlocksLeaves working
FullSale, edit, rental, storefront displayNothing — the piece is frozen
SalesSale and rentalEditing: re-photography, re-appraisal
EditEditing the recordSelling — for use mid-dispute
ViewStorefront and POS visibilityInternal access, for a legal hold
RentalRental onlyEverything else (Phase 2 relevance)

Locks are enforced in the services that sell, edit and transfer — so the register, the storefront and any future integration are all covered by one check. The reason is free text: valuation hold, repair, consignment dispute, legal hold.

The step-up challenge

High-risk actions — approving an override, changing payment keys, disabling MFA enforcement — require a second challenge: two or three symbols whose answers only trusted staff know. Both the symbol set and the list of actions it guards are configurable, and every attempt, pass or fail, is logged.

This is a second factor with a house style. The security comes from the answers being a shared secret, not from the symbols themselves — so answers are hashed, and the mechanism can be swapped for a standard authenticator step-up with a configuration change.

Deliberate departures from the brief

Each was raised at the time and agreed. None changes what the system does.

The brief saidWhat was built, and why
Laravel 11Laravel 13. Version 11 is past security support and shipped with three known advisories, including a high-severity one, fixed only in later versions.
Redis and HorizonDatabase queue. Redis is not installed on this host; the brief permits the fallback.
Tokens in tailwind.config.jsCSS-based tokens. That file does not exist in the current styling framework; the discipline it protects is enforced in the equivalent place.
A “Reveal” button for the Stripe secretNot built. It contradicted the rule that secrets are never echoed back. Keys are write-only after saving; rotation replaces them.
Five field coloursSix. Green is computed from a value, so an empty optional field needed a neutral state — otherwise an untouched record looked finished.
The design's role names and lock namesThe specification's. Confirmed with you; the design's lock names became the free-text reason.

Bugs found by running the system, not by testing it

Recorded because each would otherwise have reached production.

  • Sales tax rounding. The tax column was too narrow for a real US rate: New York's 8.875% became 8.88%, overcharging roughly three cents in every hundred dollars, on every sale.
  • Online orders never completing. Web orders belong to a Web location while stock sits in a physical shop, so payment succeeded but the order stayed unpaid and the piece stayed for sale.
  • Invisible text in the sign-in and register fields — white on white.
  • A test double that was too generous, reporting unconfirmed card payments as successful. Correcting it turned a quietly passing test into a real one.
